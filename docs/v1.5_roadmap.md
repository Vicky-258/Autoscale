# Autoscale v1.5 Roadmap

While the core predictive autoscaling engine successfully bridges RPS forecasting and deterministic Kubernetes scaling, there are four major upgrades planned for `v1.5` to make the system fully autonomous and multi-dimensional.

## Upcoming Features

### 1. Multivariate GRU Predictor
**The Goal:** Shift from predicting solely based on historical RPS to a multivariate approach.
**The Implementation:** 
Instead of inputting an `[N, 30, 1]` tensor (just RPS), we will expand the input feature space to `[N, 30, F]`. Additional features will include trailing CPU utilization, Memory pressure, and active network connections. 
**What we already have:** The localized PyTorch `GRUModel` class in `predictor/ gru_model.py` can be easily refactored by changing the `input_size` hyperparameter from `1` to `F`, and retraining the network on the expanded datasets.

### 2. Dynamic Pod Capacity Estimation
**The Goal:** Move away from hardcoding `CAPACITY_PER_POD = 100` in `config/settings.py` to a dynamic value that adjusts based on real-time computational overhead.
**The Implementation:**
A single pod's RPS capacity degrades under heavy CPU/memory states. We will write an observer module that occasionally tests max throughput vs latency, storing dynamic `CAPACITY_PER_POD` profiles depending on the exact computational state of the cluster.

### 3. Latency Guardrail Controller (via SVR Model)
**The Goal:** Prevent aggressive prediction scalings from ignoring actual user-facing latency. If the AI forecasts low RPS (so we scale down), but user latency is secretly spiking, we need a hard veto to scale back up.
**The Implementation:**
We will utilize the existing **Support Vector Regression (SVR)** system from the `performance` module. 
**What we already have:** The SVR model is already trained to map system configurations/loads directly against Pod Execution Latency. We will integrate this SVR module into the `autoscaler/policy.py` step. If the SVR flags that "Scaling down to X pods will result in latencies > latency_SLA", the SVR Guardrail will override the AI and block the scale-down.

### 4. Multi-Horizon Prediction
**The Goal:** Instead of just predicting the next 6 minutes, generate a matrix of predictions (e.g., +1min, +5min, +15min, +60min).
**The Implementation:**
A tiered decoding architecture. Instead of iterating the same GRU $t+1 \rightarrow t+12$, we will attach specialized linear heads to the GRU encoded state. 
- *Short Horizon (`+1min`)* will dictate immediate step-scaling via Docker metrics.
- *Long Horizon (`+60min`)* will be used strictly for infrastructure provisioning (e.g., spinning up new underlying bare-metal machines or allocating VMs before K8s attempts to schedule pods onto them).
