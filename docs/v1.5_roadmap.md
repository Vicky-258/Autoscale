# Autoscale v1.5 — Reliability-Centric Roadmap 🚀

While the core predictive autoscaling engine successfully bridges RPS forecasting and deterministic Kubernetes scaling, the next evolution of `Autoscale` focuses on operational trust, survivability, and production-grade behavior.

This version shifts Autoscale from:

```text
"research prototype"
```

to:

```text
"small-production-ready predictive autoscaler"
```

The focus is no longer maximizing ML sophistication.

The focus is:

* reliability
* explainability
* graceful degradation
* deployability
* operational trust

---

# Architectural Direction 🧠

`v1.5` transitions Autoscale from a reactive predictive scaler into a multi-signal orchestration layer capable of:

* demand forecasting
* latency-aware scaling
* infrastructure-awareness
* adaptive trust evaluation
* long-horizon planning
* explainable scaling decisions

The system evolves toward:

```text
Prediction + Safety + Observability + Infrastructure Awareness
```

instead of prediction-only autoscaling.

---

v1.5

## Upcoming Features

---

### 1. Reliability & Safety Layer 🛡️

**The Goal:**
Ensure the autoscaler survives bad predictions, telemetry failures, unstable workloads, and infrastructure inconsistencies without destabilizing the cluster.

---

**The Implementation:**

The controller will introduce multiple fail-safe mechanisms:

* automatic fallback to Kubernetes HPA
* stale telemetry detection
* predictor watchdog monitoring
* emergency static scaling mode
* startup warmup stabilization
* scaling instability circuit breakers
* dynamic trust scoring

Instead of treating the predictor as always correct:

```python
trust_score ∈ [0,1]
```

The system continuously evaluates:

* recent prediction accuracy
* telemetry freshness
* scaling stability
* burst consistency

If trust degrades:

* predictive authority weakens
* scaling aggressiveness reduces
* reactive scaling gains priority

This transforms the AI from:

```text
"authoritative controller"
```

into:

```text
"weighted advisor"
```

---

**Potential Risk:**
Overly aggressive trust degradation could make the predictive system too passive during volatile traffic periods.

---

**Mitigation Strategy:**
Introduce adaptive trust recovery windows and minimum predictive influence thresholds to avoid permanent fallback behavior.

---

### 2. Latency-Aware Guardrail Controller ⚡

**The Goal:**
Prevent scaling decisions from ignoring actual user-facing performance metrics such as latency and saturation.

RPS alone is not sufficient to determine production health.

---

**The Implementation:**

The existing **SVR performance model** will be integrated as a veto controller inside `autoscaler/policy.py`.

The SVR predicts whether a proposed scaling action violates latency SLAs.

### Example Logic

```python
if predicted_scale_down_causes_latency_spike:
    block_scale_down()
```

Scaling decisions become:

```text
Prediction + System Health + Latency Constraints
```

instead of prediction alone.

---

**What we already have:**

The SVR model already maps:

* workload characteristics
* system load
* replica configurations

against:

* pod execution latency

This allows direct integration without retraining the full autoscaler pipeline.

---

**Potential Risk:**
SVR latency estimates may drift over time as workload behavior evolves.

---

**Mitigation Strategy:**
Continuously compare predicted latency against observed Prometheus p95 latency metrics and trigger retraining when drift thresholds exceed acceptable bounds.

---

### 3. Adaptive Confidence Engine 📈

**The Goal:**
Replace static uncertainty assumptions with adaptive confidence estimation that reacts to real traffic volatility.

Traffic behavior changes during:

* deployments
* weekends
* cache invalidations
* regional spikes
* seasonal events

---

**The Implementation:**

Current fixed uncertainty bounds:

```text
± constant_RPS
```

will be replaced with rolling adaptive confidence estimation using:

* rolling residual windows
* percentile recalibration
* volatility-aware thresholds
* confidence decay tracking

---

**Benefits:**

* fewer false burst detections
* reduced replica thrashing
* improved anomaly sensitivity
* more stable scaling decisions

---

**Potential Risk:**
Adaptive confidence systems may become too reactive during noisy workloads.

---

**Mitigation Strategy:**
Apply smoothing windows and bounded confidence adjustment rates to avoid oscillatory behavior.

---

### 4. Multivariate Forecasting 🧩

**The Goal:**
Expand forecasting beyond historical RPS into infrastructure-aware multivariate prediction.

---

**The Implementation:**

The GRU input tensor expands from:

```text
[N,30,1]
```

to:

```text
[N,30,F]
```

New planned features include:

* RPS
* CPU utilization
* memory pressure
* network throughput
* active connections
* queue depth
* request concurrency

The localized PyTorch `GRUModel` in:

```text
predictor/gru_model.py
```

can be refactored by changing:

```python
input_size = 1 → F
```

followed by retraining on expanded datasets.

---

**The Goal of the Upgrade:**

Improve forecasting quality during:

* nonlinear load behavior
* uneven request complexity
* resource contention
* hidden saturation periods

---

**Potential Risk:**
Feature explosion may increase overfitting and training instability.

---

**Mitigation Strategy:**
Apply feature selection, normalization pipelines, and ablation testing to identify meaningful telemetry contributors.

---

### 5. Shadow Mode Validation 👀

**The Goal:**
Validate predictive behavior safely before allowing the autoscaler to control production workloads.

---

**The Implementation:**

Autoscale will support:

```text
recommendation-only mode
```

In this mode the controller logs:

* predicted replicas
* HPA decisions
* confidence state
* burst classifications
* blocked scaling actions
* latency vetoes

without modifying Kubernetes state.

---

**Benefits:**

* safe production testing
* operator trust building
* regression validation
* policy tuning

---

**Potential Risk:**
Shadow mode may diverge from real production behavior due to missing feedback loops.

---

**Mitigation Strategy:**
Replay historical scaling actions against shadow predictions to evaluate decision alignment.

---

### 6. Observability & Explainability Dashboard 📊

**The Goal:**
Make scaling behavior understandable and debuggable for operators.

Autoscalers fail operationally when humans cannot explain their actions.

---

**The Implementation:**

The dashboard will expose metrics across multiple layers.

### Prediction Layer

* predicted RPS
* actual RPS
* uncertainty envelope
* forecast accuracy

### Policy Layer

* current replicas
* recommended replicas
* trust score
* override source
* cooldown states

### System Layer

* CPU
* memory
* latency
* queue depth

---

### Example Scaling Explanation

```json
{
  "reason": "burst_detected",
  "predicted_rps": 410,
  "actual_rps": 472,
  "trust_score": 0.81,
  "scale_from": 5,
  "scale_to": 8,
  "latency_guardrail": "passed"
}
```

---

**Potential Risk:**
Large telemetry volumes may increase observability overhead.

---

**Mitigation Strategy:**
Introduce configurable metric retention and sampling policies.

---

### 7. Kubernetes-Native Integration ☸️

**The Goal:**
Transform Autoscale from a standalone Python controller into a deployable Kubernetes-native component.

---

**The Implementation:**

Planned integrations include:

* Helm chart deployment
* Prometheus exporters
* configurable CRDs
* HPA interoperability
* operator-compatible architecture
* namespace-scoped deployment support

---

**The Goal of the Upgrade:**

Reduce deployment friction for:

* homelabs
* experimental clusters
* small production systems

---

**Potential Risk:**
Deep Kubernetes integration increases operational complexity.

---

**Mitigation Strategy:**
Keep all advanced integrations optional behind modular configuration layers.

---

### 8. Multi-Horizon Infrastructure Planning 🧠

**The Goal:**
Enable the autoscaler to reason across multiple infrastructure time horizons.

Different infrastructure layers react at different speeds.

---

**The Implementation:**

Instead of a single short-term prediction stream, the GRU encoder will support specialized decoding heads for multiple prediction windows.

| Horizon | Purpose                          |
| ------- | -------------------------------- |
| +1 min  | Immediate pod scaling            |
| +5 min  | Cooldown optimization            |
| +15 min | Node prewarming                  |
| +60 min | VM / infrastructure provisioning |

---

**Long-Term Vision:**

Autoscale evolves from:

```text
pod autoscaling
```

toward:

```text
cluster capacity orchestration
```

---

**Potential Risk:**
Long-horizon forecasts may accumulate compounding prediction error.

---

**Mitigation Strategy:**
Restrict long-horizon predictions to advisory infrastructure planning rather than direct scaling authority.

---

# Explicit Non-Goals for v1.5 ❌

To avoid premature overengineering, `v1.5` intentionally avoids:

* reinforcement learning
* transformer-heavy architectures
* fully autonomous self-tuning policies
* complex ensemble predictors
* AI-only scaling authority

The focus remains:

```text
stability > novelty
```
